# Sequence ML v1 retrospective protocol

This protocol freezes the first-round five-arm development comparison before fitting this new model family. The existing WSELOB-2017 sample has prior outcome exposure; June, September and November are historical evaluation blocks, **not** an independent sealed final. The machine-readable settings are in `configs/sequence_ml_v1.json`.

## Question and common information

Does 32-message causal state history improve original-message h20 midpoint-change prediction beyond current-state models, and does a GRU improve on equally informed flattened-history Ridge/XGBoost enough to justify its cost? A0/A1 see the endpoint state. B0/B1/S0 see the same 32 states, five existing causal features and no elapsed-time channel. No arm receives raw depth or event type. All arms train and score on the same eligible source-event identities, per stock, with no cross-stock pooling.

The builder reads all causal feature states in original order within each symbol/day/segment, then requires 32 consecutive finite states ending at t. Only afterward is finite `markout_20` checked at the original event t. The target is the midpoint change 20 original messages later within a valid segment, in bp. An invalid event, feature, or segment boundary breaks a window. The GRU resets hidden state for each window. The current arms inherit the history arms' endpoint eligibility. All transformations are fit on Jan–Mar training endpoints only; April is the dev period. Dev/evaluation are sampled at original `event_index % 20 == 0`, independently of outcomes. Training endpoints are sampled by the config's day quota and seed, never by markout sign or magnitude. No raw row IDs or predictions enter Git.

## Fitting and choice

Each stock uses Jan–Mar training, April dev, and June/September/November retrospective evaluation. The 20,000-endpoint per-stock training cap was chosen before these new fits because only local CPU training is reachable in the current environment; this is one documented revision below the roadmap's 200,000 upper starting cap. Every arm receives precisely the selected endpoints. Ridge uses train-only column standardization and alpha 0.001. The current and history XGBoost arms use the same single frozen configuration in JSON. The GRU is one layer, hidden 64, with train-only feature and target standardization (predictions converted back to bp), AdamW, up to 15 epochs, dev early stopping patience 3 and seeds 7/17/29. One configuration per family means equal single-opportunity model search; any training limitation is reported rather than repaired by post-hoc search. No Transformer is included in this protocol.

For each trained seed/stock/date, retain paired Spearman IC, n, prediction scale, undefined reason and fit/inference cost. Predefined main score is equal-stock, then equal-shared-date mean stock/day IC. April selects the stronger cheap history family B* using the same full-denominator rule; each GRU seed remains separate. Report A→B as history input value and B*→S0 as architecture comparison. A mean or interval cannot silently omit undefined blocks. Pair shared dates and all five stocks in five-trading-day block bootstrap; check block-length sensitivity and report seed disagreement. This historical inference describes the inspected sample only. The planned practical delta is absolute ΔIC 0.005, not a hiring standard or a post-hoc threshold. No predictive confirmation label is available without Q5-qualified data.

Training curves, parameter/sample counts, actual CPU wall and core-hours, inference time and failed attempts accompany quality. The local macOS virtual environment loads XGBoost with `DYLD_LIBRARY_PATH=.venv/lib/python3.14/site-packages/torch/lib`, which supplies the existing bundled OpenMP runtime without changing system libraries; this is runtime setup, not a model setting. If the GRU remains optimizer-limited at epoch/budget cap, label it `TRAINING_LIMITED`; no simple-model superiority conclusion follows. Crossing/execution and broader robustness remain Q3 with separate decision units. A single training-label permutation is a pipeline negative control, not a proof against every leakage mode.
